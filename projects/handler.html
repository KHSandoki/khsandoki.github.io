Project Handler

Work-order and customer management for Taiwanese car repair shops — designed for someone standing next to a car holding a tablet, not sitting at a desk.

Honest status: this one is not finished. The domain model, database schema and migrations, and the shared validation package are complete and committed; the interface is being built now. What follows is design reasoning, not a shipped product.

The context

Small independent repair shops in Taiwan largely run on paper work orders, a whiteboard, and LINE messages. Off-the-shelf garage software exists, but it is priced and shaped for dealerships: too many fields, too many roles, and a desktop-era interface that assumes an office.

The constraint that drives everything here is the physical situation of the user. They are standing beside a car. Their hands are dirty. They are holding a tablet, one-handed, and they have about twenty seconds before going back to the job. Anything requiring precision tapping or a stable connection is a feature that will not get used.

Design decisions and why

  • PWA, tablet-first, offline-tolerant. Workshop Wi-Fi is bad, and the dead zone is always the far bay. Drafts auto-save locally, because losing a half-written work order is worse than having no software at all — one bad experience and the shop goes back to paper permanently.
  • Zod schemas shared between client and server through a pnpm workspace package. Validation defined once, imported by both sides. The failure mode this avoids is the classic one: the client thinks a field is optional, the server does not, and the error surfaces in production as an unhelpful 400.
  • Session cookies rather than JWT. A shop tablet is a shared, long-lived device that gets left on a bench. Being able to revoke a session server-side the moment it goes missing matters far more than statelessness does at this scale, and there is exactly one backend to keep state in.
  • Cursor pagination on (created_at, id). Order history only ever grows. Offset pagination gets slower every year the shop stays in business, and it silently skips rows when new orders land mid-scroll.
  • Taiwan licence plate validation covering both the older ABC-1234 layout and the newer 1234-AB one. The plate is the natural key that shop staff actually think in — they will search by plate before they search by name, every time.
  • Transactions in the service layer, not the route handlers. A work order and its line items have to land together or not at all; keeping that boundary in one place is what stops half-written orders appearing after a dropped connection.

Where it stands

An earlier iteration of this project explored a NestJS backend before I moved to plain Express with TypeScript — the framework was adding structure the problem did not have, and the layering cost more than it returned at this size.

Current state: Prisma schema and initial migration, seed data, the shared Zod schema package, and the API contract. The SvelteKit front end is the active work.
